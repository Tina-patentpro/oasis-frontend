## 一、执行摘要(突出最影响体验的 3 个问题)

1. **存在两套质量参差的"确认弹窗"实现,ChatPanel 内联用的那套是无障碍弱化版。** `src/components/chat/ConfirmationDialog.tsx` 没有用项目里那套高质量的 `AccessibleDialog`,导致焦点陷阱只认 `<button>`、遮罩过淡(`bg-black/20`)、点击遮罩会误触发"清空对话"的取消。这是清空对话、开始新对话这两条高频破坏性路径上的体验与无障碍短板(P1)。

2. **部分异步表单提交按钮在请求期间没有 disabled/loading 态,存在重复提交风险。** 最典型的是 `QuickCreateProjectDialog` 的"创建项目"按钮(`src/components/QuickCreateProjectDialog.tsx:183-190`),`onConfirm` 实际是异步建项目+刷新列表(`useWorkspaceLayout.ts:208-252`),但按钮不 disable,连点几下会建出多个项目(P1)。

3. **核心工作区是纯桌面布局,移动端/窄屏基本不可用。** `WorkspaceMainLayout` / `LeftSidebar` / `ChatPanel` 完全基于像素(`chatWidth`、`leftSidebarWidth`、拖拽 resize),全仓库没有一个 `useMediaQuery` 或移动端抽屉切换。响应式断点(sm/md/lg)只出现在设置面板和个别弹窗里。如果产品定位包含移动端使用,这是阻断性问题;若明确只面向 PC 专业用户,则可降级为 P2/已知约束(P1,取决于产品定位)。

### P1-1　两套确认弹窗并存,ChatPanel 用的是弱化版
- **【等级】** P1
- **【类别】** 交互 / 无障碍 / 视觉层级
- **【位置】** `src/components/chat/ConfirmationDialog.tsx:75-125`(被 `ChatPanel.tsx:795-816` 使用); 对照标准 `src/components/ui/feedback/ConfirmDialog.tsx` 与 `AccessibleDialog.tsx`
- **【症状】** 清空对话 / 开始新对话时弹出的确认框: 遮罩是 `bg-black/20`(几乎透不出底层),`trapDialogFocus` 只 `querySelectorAll('button')`(如果将来框里加输入框或链接,焦点陷阱会漏); 点击遮罩会触发 `onCancel`,对"确认清空对话"这种操作,点遮罩=点取消,行为可接受但与 `ConfirmDialog`(点遮罩才关)一致,问题在于这套实现没锁 body 滚动、`role=dialog` 但 `aria-modal` 缺失、不是 framer-motion 动画。
- **【根因】** 历史上有 `chat/ConfirmationDialog`(内联小弹窗,定位"贴在 chat panel 内")和 `ui/feedback/ConfirmDialog`(基于 `AccessibleDialog` 的标准弹窗)两条线,没有收敛到一套。
- **【用户体验影响】** 弱视/读屏用户在清空对话的确认框里焦点可能逸出; 普通用户会觉得这个确认框"轻飘飘的",不如设置里那些弹窗沉稳; 维护者改一处忘改另一处,行为不一致。
- **【修复建议】** 把 `ChatPanel` 里的两个 `ConfirmationDialog` 改用 `ui/feedback/ConfirmDialog`(或直接 `AccessibleDialog`),删除 `chat/ConfirmationDialog.tsx`。注意 `chat/ConfirmationDialog` 当前定位是"绝对定位在 chat panel 内、不遮全屏",如果产品确实要这种"局部确认框"形态,那就给它补上 `aria-modal`、`aria-hidden` 背景层、body scroll lock,并把 `trapDialogFocus` 换成 `useFocusTrap`。

### P1-2　异步建项目按钮无 loading/disabled,可重复提交
- **【等级】** P1
- **【类别】** 交互 / 状态完整性(disabled)
- **【位置】** `src/components/QuickCreateProjectDialog.tsx:183-190`(按钮); 触发链 `useWorkspaceLayout.ts:208-252`(`handleQuickCreateProjectConfirm` 是 async,调建项目 API + `refreshSidebarProjects`)
- **【症状】** 点"创建项目"后,按钮保持可点。若用户连点 2-3 下,会发起 2-3 次建项目请求,后端可能创建出多个同名项目。`onConfirm()` 在第 63 行同步调用后立刻 `resetForm()`+`onClose()`,但 `onConfirm` 内部是异步的,父组件并未在请求期间把弹窗锁住。
- **【根因】** `QuickCreateProjectDialog` 把"校验通过"当成"提交完成",没有暴露 `isSubmitting` 状态给按钮。
- **【用户体验影响】** 慢网下用户以为没点上、再点一次 → 列表里冒出重复项目; 或快速双击直接重复扣额/重复占用命名。
- **【修复建议】** 在 `QuickCreateProjectDialog` 内部加 `isSubmitting` state,`handleConfirm` 改 async,按钮 `disabled={isSubmitting}`、文案 `创建中…`; 或者由父组件传 `submitting` prop。对照 `InstructionLibraryPanel.tsx:289-293`(已正确做了 `disabled + aria-busy + 保存中…`)。

### P1-3　AsyncTaskMenu 的"清除已完成 / 删除记录"无二次确认
- **【等级】** P1
- **【类别】** 交互(破坏性操作)
- **【位置】** `src/components/workspace/navigation/AsyncTaskMenu.tsx:91-97`("清除已完成"直接 `clearCompletedTasks()`)、`:166-174`(每条已完成任务有"删除记录"直接 `removeAsyncTask(task.taskKey)`)
- **【症状】** 点击即删,无 ConfirmDialog。虽然这些是"已完成任务的本地记录"(可恢复性较高),但"清除已完成"是一次清掉全部已完成任务,误触成本不低。
- **【根因】** 该菜单整体定位为"任务中心查看器",把删除当轻量操作处理,没接全局 `showConfirm`。
- **【用户体验影响】** 手滑点到"清除已完成"→ 一屏任务记录消失,用户没有反悔机会(除非刷新重新拉)。
- **【修复建议】** "清除已完成"接 `ConfirmDialog`(danger=true); 单条"删除记录"可保留即时删除(轻量),但建议加一个轻量的内联确认(参考 `InstructionLibraryPanel.tsx:429-451` 的"删除→确认?"两段式,虽然那里文案略有问题见 P2-3)。

### P1-4　RechargeDialog 获取充值配置失败时静默 console.error
- **【等级】** P1
- **【类别】** 状态完整性(error)/ 交互
- **【位置】** `src/components/RechargeDialog.tsx:38-49`
- **【症状】** 打开充值弹窗时拉 `billingService.getRechargeConfig()`,失败只 `console.error`,用户侧无任何提示。后果: `rechargeConfig` 保持 `null`,自定义金额的最低/最高限额提示只能 fallback 到"(最低1元)"(`:214`),赠送规则也无法计算(`:256` 的 `rechargeConfig.enable_bonus === 1` 判断直接不渲染赠送提示)。用户可能按错误的心智模型充值。
- **【根因】** 异步副作用没走 `useAsyncState` 的 error 通道(对照 `HistoryDataDialog.tsx:66-69` 的标准做法),异常被吞。
- **【用户体验影响】** 配置接口挂了,用户看到的是一个"看起来正常但限额/赠送规则都不对"的充值页,可能充错金额、误以为有赠送。
- **【修复建议】** 改用 `useAsyncState`,error 时在弹窗内展示"配置加载失败,请重试"+ 重试按钮; 或至少在 `catch` 里 `notify('充值配置加载失败,显示的金额规则可能不准确')`。

### P1-5　核心工作区无移动端/窄屏适配(取决于产品定位)
- **【等级】** P1(若产品含移动端)/ P2(若明确 PC-only)
- **【类别】** 响应式
- **【位置】** `modules/workspace/components/WorkspaceMainLayout.tsx`(无断点)、`hooks/useWorkspaceLayout.ts`(`chatWidth`/`leftSidebarWidth` 全像素)、`ChatPanel.tsx:1311`(`style={{ width }}` 固定像素)
- **【症状】** 全仓 `grep` 无 `useMediaQuery`、无 `matchMedia`。窗口缩到 800px 以下: 左栏 + 中间输入输出 + 右侧 chat 三栏会挤成一团,chat panel 的固定 `width` 会把中间内容压没。设置面板(`SettingsPanel.tsx:123`)和若干弹窗(`HistoryDataDialog`、`EditProjectDialog`、`PasswordCard`)有 `sm:/md:/lg:` 断点,但主工作台没有。
- **【根因】** 这是一个专业专利撰写工具,默认假设宽屏 + 多栏并排; 移动端从未进入设计范围。
- **【用户体验影响】** 平板/小笔记本竖屏、或浏览器窗口没最大化时,工作区不可用或需要频繁横向滚动。
- **【修复建议】** 先确认产品定位。若需要支持窄屏: 在 `useWorkspaceLayout` 引入 `matchMedia('(max-width: 1024px)')`,窄屏时强制 `chatMode` 切到隐藏/抽屉式、左栏改为可折叠 overlay; `WorkspaceMainLayout` 在窄屏把 `flex-row` 降级为 `flex-col` 或 tab 切换。

### P2-1　ProjectCard 整卡用 `<div onClick>`,键盘/读屏可达性弱
- **【等级】** P2
- **【类别】** 无障碍(键盘可达性)
- **【位置】** `src/components/workspace/left-sidebar/management/ProjectCard.tsx:167-170`(`<div className="p-3 cursor-pointer" onClick={handleProjectCardClick}>`)
- **【症状】** 整张项目卡是一个带 `onClick` 的 `<div>`,没有 `role`、没有 `tabIndex`、没有 `onKeyDown`。键盘用户 Tab 进不去这张卡,读屏软件不会把它读成"可操作项"。卡内部的展开按钮、名称按钮、菜单按钮是分别可达的,但"点空白区选中项目"这个主交互键盘做不了。
- **【根因】** 用 `div+onClick` 比 `<button>` 更容易包裹复杂子元素,于是走了捷径。
- **【用户体验影响】** 纯键盘用户无法选中项目(虽然能用回车进名称按钮,但交互模型不一致); 读屏用户感知不到"这是个可点的卡片"。
- **【修复建议】** 给这个 div 加 `role="button" tabIndex={0}` 和 `onKeyDown`(Enter/Space 触发 `handleProjectCardClick`),`aria-label={\`项目:${project.name}\`}`; 或把"选中"职责完全交给已有的名称按钮,去掉 div 的 onClick。

### P2-2　NavigationBar 用户菜单图标 SVG 未标 aria-hidden
- **【等级】** P2
- **【类别】** 无障碍(装饰元素)
- **【位置】** `src/components/workspace/NavigationBar.tsx:214-224`(用户头像 SVG)、`src/components/workspace/OutputSection.tsx:288-298`(空状态文档图标 SVG)
- **【症状】** 这些是纯装饰图标,按钮本身已有 `aria-label`(NavigationBar 那个),但 SVG 没加 `aria-hidden="true"`。部分读屏在遇到无 `aria-hidden` 的内联 SVG 时会尝试读 `<path>`,造成冗余朗读。项目其它地方(如 `EmptyChatState.tsx:58`、`ChatConversationPane.tsx:67`)都规范地加了 `aria-hidden`,这两处漏了。
- **【根因】** 个别遗漏,非系统性。
- **【用户体验影响】** 读屏用户可能听到多余的图标描述噪音。
- **【修复建议】** 给这两处 `<svg>` 加 `aria-hidden="true"`。另外 `OutputSection.tsx:297` 那条 path 数据看起来可疑(文档图标的 path 末尾坐标异常,可能渲染出一个畸形图标),建议一并用标准 lucide `file-text` 图标替换并验证。

### P2-3　加载/保存文案省略号不统一
- **【等级】** P2
- **【类别】** 文案一致性
- **【位置】** 多处: `正在加载...`(`HistoryDataDialog.tsx:389`、`ProjectCard.tsx:371`)、`加载中…`(`InstructionLibraryPanel.tsx:305`)、`正在加载…`(`tabs.tsx:70/477`)、`保存中…`(`InstructionLibraryPanel.tsx:292`)vs `保存中...`(`PasswordCard.tsx:148`); 另 `InstructionLibraryPanel.tsx:439` 的删除二次确认文案是 `确认?`(带英文问号、缺主语),与 `ConfirmDialog` 默认的 `确认` 不一致。
- **【症状】** 中文省略号 `…`(U+2026)和三个英文句点 `...` 混用; "加载中/正在加载"两种说法混用; "确认/确认?/确定"三种确认词混用。
- **【根因】** 没有统一的文案字典,各组件随手写。
- **【用户体验影响】** 细节不一致,显得不精致; 不影响功能。
- **【修复建议】** 统一为: 加载用 `加载中…`(U+2026)、保存用 `保存中…`、确认主操作统一用 `确认`。`InstructionLibraryPanel` 的 `确认?` 改为 `确认删除`。建议在 `constants/` 下建一个 `copy.ts` 集中管理。

### P2-4　ChatSearchBar 用 autoFocus 且无焦点陷阱
- **【等级】** P2
- **【类别】** 无障碍(焦点管理)/ 交互
- **【位置】** `src/components/chat/ChatConversationPane.tsx:72-94`(`autoFocus` 在 input 上)、整个 `ChatSearchBar` 没用 `useFocusTrap`
- **【症状】** 打开搜索(Ctrl+Shift+F)后,`autoFocus` 把焦点放到输入框,但 Tab 会跳出搜索栏回到聊天主体; Esc 能关(`:84-87` 已处理)这点是好的。`autoFocus` 在 React 里有时会和弹窗的焦点恢复打架。
- **【根因】** 搜索栏定位为"轻量浮层"而非弹窗,没走 trap。
- **【用户体验影响】** 键盘用户搜索时 Tab 一下就跑出去了,得重新点回来。
- **【修复建议】** 给搜索栏加 `useFocusTrap(searchOpen)`(项目已有这个 hook,`hooks/useFocusTrap.ts`),或至少在 onBlur 失焦到外部时自动关闭。

### P2-5　UserMenuPanel 的强制重载确认弹窗与面板同层 z-index
- **【等级】** P2
- **【类别】** 视觉层级
- **【位置】** `src/components/workspace/navigation/UserMenuPanel.tsx:204`(用户菜单面板 `z-50`)+ `:427-457`(内部 `AccessibleDialog` 默认 `z-50`)
- **【症状】** 用户菜单面板是 `z-50`,它内部弹出的"确认强制重新加载"`AccessibleDialog` 也是默认 `z-50`。理论上后渲染的 DOM 会在上层,`AccessibleDialog` 用了 `fixed inset-0` 全屏遮罩,实际渲染问题概率低; 但同层级是隐患,未来若有人给 `AccessibleDialog` 传 `zIndexClassName` 覆盖时容易出问题。对照 `SessionExpiredDialog.tsx:42` 显式用了 `z-[120]` 来确保最顶层——这种"显式提升"的纪律没贯彻到所有内嵌确认弹窗。
- **【根因】** z-index 没有全局约定表,各组件用默认值。
- **【用户体验影响】** 当前基本不会出问题,但维护时易踩坑。
- **【修复建议】** 建立 z-index 层级常量(如 `Z.dropdown=40, Z.popover=50, Z.modal=60, Z.toast=80, Z.sessionExpired=120`),强制重载确认弹窗用 `Z.modal`。

## 七、整体 UI 健康度评分:**8 / 10**

**理由(白话):**
- **加分项(显著高于业内平均):** 项目有一套设计精良的 UI 基础原语(`AccessibleDialog`、`ActionButton`、`useFocusTrap`、`LoadingSpinner`、`ConfirmDialog`),focus trap 用了模块级栈来协调嵌套弹窗、MutationObserver 处理懒加载内容——这是相当成熟的实现。认证表单、`InstructionLibraryPanel`、`HistoryDataDialog`、`OutputSection` 是状态完整性和无障碍的范本(loading/empty/error/disabled 四态全有,aria-invalid/aria-describedby/role=alert 齐全)。错误边界、全局 `getErrorMessage`、Sentry 上报、组件级 retry fallback 都到位。测试覆盖广(几乎每个组件都有 .test.tsx)。
- **扣分项(2 分):** 一是"两套确认弹窗没收敛 + 个别异步表单忘了 disabled"这类**一致性问题**(P1-1/2/3),说明原语有了但没强制全员使用; 二是**移动端/窄屏完全没适配**(P1-5),若产品要移动端就是硬伤。剩下的 P2 都是装饰图标漏 aria-hidden、文案省略号不统一这类**细节打磨**问题。
- **没扣到分的关键点:** 没发现任何白屏、静默吞错导致数据丢失、focus 永久丢失、键盘完全不可用等阻断性问题。整体是一个"工程纪律良好、偶有遗漏"的成熟前端项目。

**优先修复顺序建议:** P1-1(收敛确认弹窗)→ P1-2(建项目按钮 disable)→ P1-4(充值配置错误态)→ P1-3(任务删除二次确认)→ P1-5(确认移动端定位后再决定)→ P2 批量打磨。
