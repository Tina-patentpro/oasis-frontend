# API 设计评审清单（D6）

最后更新：2025-10-22  
适用范围：所有新增或变更的 OpenAPI 文档，在提交评审或合并前执行一次完整检查。

## 使用方式

1. 将本清单复制到评审 PR/需求单中，逐项确认。
2. 若某项不适用，请说明原因并记录补救措施。
3. 评审结束后，将结论同步到 `CHANGELOG.md` 或会议纪要。

## 评审清单

| 类别     | 编号 | 检查点                                                                      | 说明与建议                                             |
| -------- | ---- | --------------------------------------------------------------------------- | ------------------------------------------------------ |
| 需求映射 | R1   | 是否在 `INDEX.md` 中补充设计目标映射？                                      | 新增接口需在索引添加 Visibility、Owner 与主要路径。    |
| 需求映射 | R2   | 是否提供业务背景/约束？                                                     | 更新 `BUSINESS-RULES.md` 或在文档中写明关键字段约束。  |
| 请求定义 | Q1   | 是否声明 `security` 与认证方式？                                            | 所有受保护接口需配置 `BearerAuth` 或特定 scheme。      |
| 请求定义 | Q2   | 必填参数是否标明 `required` 或在 Schema 中限制？                            | 避免仅在文档描述里写必填；应通过 schema 标注。         |
| 请求定义 | Q3   | 是否为查询参数定义类型、范围、默认值？                                      | 特别注意分页、排序、过滤的枚举值。                     |
| 响应结构 | S1   | 是否复用统一响应模板（`ApiResponse/ErrorResponse`）？                       | 统一结构便于前端与监控解析。                           |
| 响应结构 | S2   | 是否提供成功 + 错误示例？                                                   | 至少提供一个典型成功响应；关键错误码需示例。           |
| 错误处理 | E1   | 错误码是否遵循模块前缀规范？                                                | 参考 `ERROR-HANDLING.md`，避免重复或不明语义的错误码。 |
| 错误处理 | E2   | 是否标记潜在的限流/配额返回？                                               | 当接口受限流保护时需文档化 `429` 响应。                |
| 安全     | A1   | 是否检查敏感字段（token、密钥）不会被记录或回传？                           | 在描述中指明脱敏或遮蔽策略。                           |
| 安全     | A2   | 是否遵循最小权限原则？                                                      | 若接口仅限管理员，需要 `x-required-role` 或文档说明。  |
| 性能     | P1   | 是否在关键接口添加 `x-performance` 或在 `PERFORMANCE-METRICS.md` 更新目标？ | 确保 SLA 与监控目标一致。                              |
| 性能     | P2   | 是否评估批量接口的分页/分片策略？                                           | 避免一次性返回超大数据。                               |
| 测试     | T1   | 合约测试是否覆盖关键路径？                                                  | 新增合约测试或扩展现有脚本。                           |
| 测试     | T2   | 是否在 CI 中配置自动执行（见 `Automation.md`）？                            | 确保回归时自动校验。                                   |
| 文档     | D1   | `CHANGELOG.md` 是否记录变更？                                               | 标注版本号、责任人及影响。                             |
| 文档     | D2   | 是否在 README/索引中暴露新文档？                                            | 便于第三方快速查阅。                                   |
| 文档     | D3   | 是否提供示例（cURL/SDK）？                                                  | 针对关键场景提供复制即用示例。                         |
