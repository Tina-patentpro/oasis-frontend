### 3. 完善高风险问题的背景和影响分析 [重要]

**现状:** open-questions.md列出问题但缺少背景和影响分析

**建议:**

```
补充内容到：docs/api/open-questions.md
```

**改善示例（以"链式调用参数映射"为例）:**

````markdown
### Q1: 链式调用参数映射格式是否支持表达式？

**背景:**
设计目标3.e要求"链式调用"支持参数自动映射。
例如：workflow A的输出字段`claims`需要映射到workflow B的输入字段`draftInput`

**问题描述:**

1. 映射格式是否支持简单赋值？
   ```json
   { "targetField": "draftInput", "source": "prev.outputs.claims" }
   ```
````

2. 是否需要支持转换表达式？例如：
   ```json
   {
     "targetField": "draftInput",
     "source": "prev.outputs.claims",
     "transform": "input | uppercase | truncate(100)"
   }
   ```

**影响范围:**

- 前端表单设计：需要在UI中提供表达式编辑器
- 后端实现：需要集成表达式引擎（如 JSONata / JMESPath）
- API设计：workflows.yaml中POST /api/workflow-chains的mapping字段

**关键决策点:**

- 决定是否支持表达式 → 影响系统复杂度和可扩展性
- 选择表达式语言 → 影响开发工作量和学习成本
- 定义支持的操作符 → 影响用户可配置的灵活度

**建议讨论顺序:**

1. 先确认是否需要表达式（简单赋值是否足够？）
2. 确认后再选择表达式语言和操作符

**参考实现:**

- Zapier: 支持 Formatter (简单操作) 和 Code (JavaScript)
- IFTTT: 支持条件和操作符
- Automation Anywhere: 支持表达式语言

```

**预期效果:**
- 为后端/产品评审提供充分的背景
- 加快决策效率
- 避免反复评审

**实现成本:** 中等（1.5小时）

### 4. 添加错误处理最佳实践指南 [重要]
**现状:** error-codes.md列出错误码，但缺少处理建议

**建议:**
```

新增文件：docs/api/ERROR-HANDLING-GUIDE.md

````

**改善内容:**
```markdown
# 错误处理指南

## 前端处理建议

### 认证错误（401/403）
- 清空本地token
- 重定向到登录页
- 显示友好提示："会话已过期，请重新登录"

### 业务逻辑错误（400/409）
- 展示error.message给用户
- 例：WF-409-01 → "工作流执行中，请稍候"

### 服务异常（500/502）
- 显示："暂时无法处理，请稍后重试"
- 自动重试（exponential backoff）
- 收集错误ID用于后续排查

## 后端处理建议

### 规范错误响应
```json
{
  "success": false,
  "error": {
    "code": "WF-409-01",      // 规范的错误码
    "message": "Workflow is already running",  // 用户友好的消息
    "details": {              // 可选的详细信息
      "workflowId": "wf-123",
      "currentExecutionId": "exec-456"
    },
    "timestamp": "2025-10-22T10:30:00Z",  // 便于排查
    "requestId": "req-789"    // 追踪ID
  }
}
````

### 重试策略

- 409冲突：建议client端重试，建议间隔5秒
- 502网关错误：自动重试，指数退避（1s, 2s, 4s, 8s）
- 500服务异常：返回Retry-After头

## 监控和告警

### 应关注的错误

- 500/502：立即告警，影响服务
- 409冲突频繁：可能业务逻辑有问题
- 401认证失败多次：可能被攻击

```

**预期效果:**
- 统一的前后端错误处理标准
- 更好的用户体验
- 便于故障排查

**实现成本:** 低-中（1小时）

**建议:**
```

新增文件：docs/api/SECURITY-CONSIDERATIONS.md

````

**改善内容:**
```markdown
# 安全性考虑

## 认证与授权
- [ ] 所有endpoint都需要Bearer Token认证
- [ ] Token过期时间建议：15分钟
- [ ] 刷新token机制：需要refresh_token端点
- [ ] 权限检查：细粒度权限（resource-level）

## 数据保护
- [ ] 敏感字段加密：密码、支付信息
- [ ] 文件下载：需要签名URL或短期Token，防止目录遍历
- [ ] 日志脱敏：不记录token、密码、credit card信息

## 速率限制
- 建议：用户级别限制 (e.g., 100 requests/minute)
- 工作流执行：限制并发数 (e.g., max 5 concurrent)

## 输入验证
- [ ] 参数schema校验（已在workflows.yaml中定义）
- [ ] 文件上传：限制大小、扩展名、MIME类型
- [ ] SQL注入防御：使用参数化查询

## 第三方集成安全
- [ ] Dify API调用：使用service account，定期轮换密钥
- [ ] 支付网关：PCI合规，敏感数据不流经自有系统
````

**预期效果:**

- 提高系统安全性
- 符合合规要求
- 减少安全隐患

**实现成本:** 低-中（1.5小时）
