## 🎯 核心功能需求

### 1. Dify 工作流/对话流后台支撑

1. 使用 Dify 作为 AI 生成任务后台，阿里云RDS Supabase=PostgreSQL 作为后台基础和数据库，对象存储 OSS 作为文件服务.
2. Dify workflow（工作流）调用、Dify Chatflow（对话流）调用是主要功能。调用 API 信息由管理后台提供给前端。确保 API 信息不在浏览器暴露。

### 2. Dify 工作流功能

围绕 Dify workflow 功能，提供：

#### 2.1 工作流分类与选择

- **a.** 左边栏中工作流分类和选择的内容，由管理后台进行预设。用户选择后，前端自动在中栏向管理后台调用对应的 API
- **实现状态：** ✅ 前端已实现左侧边栏动态分类与选择逻辑

#### 2.2 动态输入表单

- **b.** 中栏输入框根据 API 的输入参数要求，由管理后台进行预设，动态调整输入卡片，可选择输入文本、文件和/或图片
- **实现状态：** ✅ 前端已实现动态表单渲染与文件上传组件

#### 2.3 历史数据读取

- **c.** 可选择读取与工作流有关联的，根据项目设定或版本管理，历史数据（包含数据和/或文件）作为输入参数。读取时，根据 API 的输入参数要求，由管理后台进行预设，自动进行筛选
- **实现状态：** ✅ 前端已实现历史数据对话框与自动回填逻辑

#### 2.4 文件下载

- **d.** 可以选择下载存储在文件服务的由工作流生成或获取的文件
- **实现状态：** ✅ 前端已实现文件下载对话框与批量下载功能

#### 2.5 输入输出参数规模

- **e.** 输入输出参数≤200 个，可能是数据、文件和/或图片
- **实现状态：** ✅ 前端支持大规模参数处理

#### 2.6 数据标记与版本管理

- **f.** Dify 输出数据在记录到 PostgreSQL 数据库时需要标记 `sys.user_id`、`sys.app_id`、`sys.workflow_id` 和 `sys.workflow_run_id`，生成时间。后台 SqlServer 数据库需要根据这些信息进行分类，排序和版本管理
- **实现状态：** 🔄 需后端实现

#### 2.7 工作流链式调用

- **g.** 可以根据管理后台的预设，在用户点击下一步后，自动将本工作流生成的输出，和关联（基于版本管理）的其他需要内容填入下一工作流的输入参数中
- **实现状态：** ✅ 前端已实现链式调用与参数自动传递逻辑

#### 2.8 实时进度展示

- **h.** 通过 API 启动工作流时，将后台赋予的用户编号和会话编号作为入参输入。工作流启动后，在第一个节点通过 HTTP 返回里程碑链设置（Array），在预设的里程碑（多个）设置 http 节点，基于会话编号连接网站并通知网站里程碑达到。网站根据收到的信息显示工作流节点链和生成进度。如果出现故障，则显示 `sys.workflow_run_id` 和故障编号
- **实现状态：** ✅ 前端已实现流式进度展示与步骤状态可视化

### 3. Dify 对话流功能

## 🏗️ 前端架构特性

### 组件化设计

- **模块化结构：** 按功能域划分模块（workspace、auth、admin 等）
- **组件复用：** 抽取通用 UI 组件库（`src/components/ui/`）
- **懒加载：** 路由级和对话框级代码分割

### 状态管理策略

- **全局状态：** 使用 Zustand 管理跨组件状态
- **本地状态：** React Hooks 管理组件内部状态
- **服务层：** 统一 API 服务封装（`src/api/services/`）

### 性能优化

- **虚拟化：** 长列表使用虚拟滚动（react-window）
- **缓存策略：** HTTP 缓存 + 本地存储结合
- **Bundle 优化：** 代码分割 + Tree Shaking
- **性能监控：** 实时性能指标采集与可视化

### 错误处理

- **多层次错误边界：**
  - PageErrorBoundary：页面级
  - ComponentErrorBoundary：组件级
  - AsyncBoundary：异步操作级
- **友好错误提示：** 用户可理解的错误信息
- **错误上报：** 集成性能监控系统

### 响应式设计

- **适配方案：** Tailwind 响应式工具类
- **布局模式：** 水平/垂直布局自适应
- **触摸优化：** 移动端触摸事件支持
