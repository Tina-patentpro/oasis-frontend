# Stage D (D35–D40) API 与前端体验治理手册

## 背景与目标

- Stage D 聚焦长期可控的接口与前端体验治理，确保跨团队协同、变更留痕、网络体验持续改进。
- 阶段核心指标：接口变更记录覆盖率 **100%**、季度回归通过率 ≥ **95%**、HTTP/2 + Brotli 上线后首屏传输体积再降 ≥ **15%**。
- 本手册与配套文档（评审日历、订阅机制、网络优化计划）共同构成治理闭环。

## 核心原则

1. **流程先行**：所有 API 及体验变更须先提审设计，获批后才能进入实现与合并。
2. **文档落地**：变更通过后必须同步更新 `docs/CHANGELOG.md` 与 `docs/api/CHANGELOG.md`，并触发订阅通知。
3. **数据驱动**：Web Vitals、CI、冒烟回归用于衡量治理成效；未达标需在下一轮季度评审给出整改方案。
4. **透明协作**：前端牵头协调后端、运维、产品；风险看板和会议纪要向全员开放。

## 组织与职责（RACI）

| 流程节点                             | Frontend Lead | Backend Lead | DevOps | Product | QA / SRE |
| ------------------------------------ | ------------- | ------------ | ------ | ------- | -------- |
| 需求/设计评审（含 API 草案）         | **R**         | **A**        | C      | **C**   | C        |
| PR 审查（api:validate / Web Vitals） | **A**         | **R**        | C      | I       | C        |
| 变更登记与订阅通知                   | **R**         | C            | C      | I       | I        |
| 季度回归与复盘                       | **A**         | **C**        | C      | **R**   | **C**    |
| 风险看板（SSE / 支付 / 权限）        | **A**         | **R**        | **C**  | **I**   | **C**    |

> 说明：R=Responsible，A=Accountable，C=Consulted，I=Informed。

## Stage D 治理流程

1. **设计与需求准入**
   - 前端牵头统一在看板创建需求卡片，附接口草案或体验稿。
   - 必须在卡片中链接到最新的风险看板条目，确认是否触发额外评审。
2. **实现与 PR 审查**
   - 所有 PR 使用更新后的模板，必须勾选 `Stage D 治理核对` 中的 api:validate 与 Web Vitals。
   - 未勾选或无证据的 PR 不得合并；必要时附带 `docs/governance/CHANGELOG-SUBSCRIPTION-MECHANISM.md` 中的通知截图。
3. **合并与变更登记**
   - 合并后 24 小时内更新 `docs/CHANGELOG.md`、`docs/api/CHANGELOG.md`，并通过订阅机制推送。
   - 若变更涉及网络层，需同步更新《Stage D 网络优化实施方案》执行状态。
4. **回归与监控**
   - 回归用例以季度回归包为准；回归通过率低于 95% 时触发专项复盘。
   - Web Vitals、SSE 错误率、支付/权限告警纳入每周例会。

## 风险看板（迭代要求）

| 风险域 | 措施与检查点                                   | 更新节奏     | 负责人       |
| ------ | ---------------------------------------------- | ------------ | ------------ |
| SSE    | 覆盖断线重连、回退路径；评审订阅消息结构兼容性 | 双周（周三） | Backend Lead |
| 支付   | 对接风控、超时与补偿策略；回顾对账脚本         | 月度第 2 周  | Product + QA |
| 权限   | 校验角色矩阵、token 生命周期、敏感接口访问日志 | 月度第 4 周  | DevOps + SRE |

每次更新须附评审纪要，归档至 `docs/governance/logs/YYYY-MM-DD.md`（若目录不存在可在首次迭代创建）。

## 成熟度度量与数据采集

- **接口变更覆盖**：CI 中比对 `docs/api/CHANGELOG.md` 的最近提交，缺失时提醒。抽样审计每两周执行一次。
- **季度回归通过率**：QA 汇总 `run/regression` 报告；低于 95% 需在下次评审提交 `CAPA`。
- **网络体积指标**：基于 `npm run build:analyze` 与 WebPageTest/Chrome UX Report 统计首屏传输体积，归档至 `docs/perf/`。
- **体验指标**：监控 LCP、INP、CLS；超出阈值时创建跟进 issue 并在下一次评审追踪。

## 协作机制

- **日常渠道**：Slack `#api-governance`（技术），飞书群《产品体验协同》（跨部门），Jira 看板「Stage D」列队。
- **会议节奏**：详见《Stage D 季度评审日历》；临时风险通过 Slack/飞书 @ 所有责任人。
- **文档共建**：所有治理文档放置于 `docs/governance/`，提交时需在 PR 描述中链接并说明变更。

## 持续改进

- 每季度评审会最后保留 15 分钟收集流程改进建议。
- 对于触发 SLA 的事件，需在 5 个工作日内完成根因分析，并将结论补充至风险看板。
- 本手册每季度与评审日历一同复核；如有破坏性调整，需经前端/后端/运维负责人共同签字确认。
