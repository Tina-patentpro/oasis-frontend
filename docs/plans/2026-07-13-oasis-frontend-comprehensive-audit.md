# 1. 结论：原计划是否足够全面

## 1.1 总体判断

**原计划在审计域覆盖上基本全面，但在执行决策、证据边界、失败分流和最终状态判定上仍不完整，不能直接作为“另一名工程师无需再做关键决策即可执行”的正式审计规程。**

原计划已经覆盖：

* 基线冻结；
* 架构与工具盘点；
* 类型、Lint、测试、构建、API、安全等静态门；
* 正确性、状态、授权、维护性审查；
* build 后 preview 与 Playwright；
* WCAG、性能、ASVS、监控和发布能力；
* P0-P3 报告输出。

但它仍更接近**高质量目录**，而不是**闭环执行协议**。主要不足是：

1. 未定义哪些检查是强制项、条件项、仅在获得生产证据后才能判定的项目。
2. 未建立脚本副作用审查机制，可能误执行联网、发布或远程写入命令。
3. 未区分脚本的调用关系，可能重复执行 `test`、`test:ci`、`test:unit`、`test:integration`，造成时间浪费或结论重复。
4. 未定义浏览器覆盖的具体旅程、角色、数据状态、网络状态和响应式组合。
5. 未定义失败重跑、偶发失败、超时、资源不足和环境故障如何分类。
6. 未规定证据文件格式、证据编号、时间戳、命令退出码、日志脱敏和可追溯性。
7. 未说明本地 Lighthouse 或 Playwright 性能结果不能替代生产环境 Core Web Vitals p75。
8. 未说明前端仓库无法单独证明全部 OWASP ASVS 5.0 控制符合。
9. 未给出最终五种质量状态的排他性决策树。
10. “监控与发布回滚能力”可能超出前端仓库本地可验证范围。
11. 未规定如何保护审计期间产生的 `dist`、coverage、trace、截图等文件，避免污染仓库或误删原有文件。
12. 未给出“全面审计”的量化覆盖边界，容易把风险抽样误写成全量覆盖。

因此：

> **原计划不应直接执行。应采用下述增强版计划，将其升级为证据优先、风险驱动、分层判定、默认只读的审计规程。**

# 3. 证据分层与结论边界

## 3.1 证据层级

| 层级 | 名称             | 典型证据                                             | 可以证明                  | 不可以证明              |
| -- | -------------- | ------------------------------------------------ | --------------------- | ------------------ |
| E0 | 计划证据           | 计划、范围、命令表、抽样矩阵                                   | 审计准备充分                | 项目实际质量             |
| E1 | 静态/本地证据        | 源码审阅、类型、Lint、单测、构建、依赖扫描                          | 当前提交在本地工具下的静态结果       | 用户真实行为、生产配置和真实 p75 |
| E2 | preview 浏览器证据  | 生产构建 preview、Playwright、截图、trace、console、network | 生产构建在受控浏览器环境的行为       | 真实账号、生产网关、CDN、生产数据 |
| E3 | 真实账号 Chrome 证据 | 专用账号、真实 Chrome、真实后端但受控数据                         | 账号、SSO、真实接口和浏览器差异     | 全体用户、生产流量统计和发布回滚   |
| E4 | 生产/外部控制台证据     | RUM、CrUX、监控、错误平台、部署和回滚记录                         | 生产 p75、真实错误、部署与监控实际状态 | 未覆盖的用户群、未来稳定性      |

## 3.2 不可跨层替代规则

1. E1 测试通过不能替代 E2 用户旅程通过。
2. E2 本地 preview 通过不能替代 E3 真实账号链路。
3. E2 Lighthouse 或 Playwright 指标不能替代 E4 Core Web Vitals p75。
4. E1 前端权限判断不能证明服务器端授权正确。
5. E1 发现的缺陷不会因为 E2 暂未复现而自动关闭。
6. E3 单一账号通过不能证明其他角色、租户或权限组合通过。
7. 自动化无障碍扫描不能独立证明 WCAG 2.2 AA 合规。
8. 扫描器无漏洞不能证明不存在业务逻辑漏洞或服务端漏洞。

# 5. 增强版分阶段执行计划

# 阶段 0：审计治理与只读边界冻结

## 目标

确保审计不会修改业务源码、提交、远程环境或无关文件，并建立统一证据协议。

## 具体动作

1. 建立仓库外的证据目录，例如：

```text
%TEMP%\oasis-frontend-audit-20260713-<HHmmss>\
```

2. 记录：

   * 仓库绝对路径；
   * 当前分支；
   * HEAD；
   * 工作树、暂存区及全部未跟踪文件；
   * Git、Node、包管理器、操作系统、Chrome、Playwright 版本；
   * 时区、语言、屏幕缩放；
   * `package.json` 和锁文件哈希。
3. 明确禁止：

   * `git reset`；
   * `git clean`；
   * `git checkout --`；
   * 自动修复型 Lint；
   * 快照更新；
   * 依赖升级；
   * 发布、部署、推送、标签创建；
   * 生产数据写入；
   * 源码上传到第三方扫描服务。
4. 对每个脚本先执行文本审查，不因脚本名称带有 `check`、`scan`、`release` 就假定其只读。
5. 为所有发现和证据定义编号：

   * 发现：`F-P1-001`；
   * 命令：`CMD-001`；
   * 浏览器证据：`BR-E2-001`；
   * 源码证据：`SRC-001`。

## 原因

“审计不修复”只有在命令副作用、生成物、账号操作和 Git 状态都受到约束时才成立。

# 阶段 1：项目结构、脚本与覆盖契约盘点

## 目标

在运行命令前形成完整的项目地图、审计范围、脚本调用图和风险优先级。

## 具体动作

1. 检查：

   * `package.json`；
   * `packageManager` 字段；
   * 锁文件；
   * Node 版本约束；
   * Vite、Jest、Playwright、TypeScript、ESLint 配置；
   * `.env*` 示例和环境变量读取点；
   * 路由定义；
   * Zustand store；
   * API client、拦截器、生成代码及 schema；
   * 全局错误边界；
   * 懒加载与 chunk 划分；
   * 设计令牌和全局样式；
   * 测试目录、fixtures、mocks；
   * 构建、发布、监控和安全脚本。
2. 展开全部质量脚本的调用关系：

   * 直接命令；
   * 递归调用的其他 npm scripts；
   * 是否联网；
   * 是否写文件；
   * 是否依赖账号、令牌或外部服务；
   * 是否启动 dev server 或 preview；
   * 是否隐式更新快照或生成 API 文件。
3. 确定包管理器：

   * 优先使用 `package.json.packageManager`；
   * 无该字段时，只允许依据唯一锁文件确定；
   * 多锁文件且无明确声明时，停止依赖恢复并报告。
4. 建立覆盖清单：

   * 100% 路由入口；
   * 100% API client 和鉴权边界；
   * 100% Zustand store；
   * 100%上传、下载、提交、删除、权限和账号切换代码；
   * 100%全局错误处理和监控接入；
   * 核心用户旅程相关组件全量；
   * 其他低风险展示组件按风险抽样。
5. 建立风险评分：

```text
风险分 = 业务影响 0-3
       + 权限或敏感数据 0-3
       + 异步/并发复杂度 0-2
       + 调用覆盖面 0-2
       + 测试缺口 0-2
       + 最近变更或高耦合 0-2
```

* 分数 ≥6：必须深入审阅；
* 身份、权限、API、store、上传、下载、提交、删除：无论分数均深入审阅；
* 业务影响判断无法确认时标记“需现场确认”，并采用较高一档风险。

## 原因

不先了解脚本语义和代码结构，就无法确定命令是否安全，也无法证明“全面审计”的覆盖范围。

## 输入

* 仓库配置、源码目录结构、脚本定义；
* 阶段 0 基线。

## 输出

* `architecture-map.md`；
* `route-inventory.csv`；
* `store-inventory.csv`；
* `api-inventory.csv`；
* `script-dag.md`；
* `script-side-effects.csv`；
* `risk-register.csv`；
* `coverage-contract.md`。

## 验收标准

* 所有用户列出的质量脚本均已定位并解释；
* 已明确哪些脚本会被其他脚本完整包含；
* 已明确 Playwright 实际使用 dev、preview 或外部 URL；
* 所有核心路由、store 和 API 入口进入覆盖台账；
* 所有未知项均明确标记“需现场确认”。

## 停止条件

* `package.json` 或配置不可解析；
* 脚本包含未获允许的部署、发布、删除或远程写入行为；
* 包管理器或锁文件存在无法解决的冲突；
* 必须的环境变量只能从生产密钥取得。

## 证据层

E0、E1。

# 阶段 2：依赖恢复与本地质量门

## 目标

以可复现、无依赖图漂移的方式运行本地静态和自动化质量门。

## 具体动作

## 2.1 依赖恢复

仅使用冻结模式：

* npm：`npm ci`
* pnpm：`pnpm install --frozen-lockfile`
* Yarn：`yarn install --immutable`

实际命令依据阶段 1 确定的包管理器。

依赖安装前后重新计算：

* `package.json` 哈希；
* 锁文件哈希；
* Git 状态。

## 2.2 推荐执行顺序

以下 `<PM_RUN>` 表示项目实际包管理器的脚本执行方式。

```text
1. scripts:test
2. type-check
3. lint
4. api:validate:ci
5. api:drift:strict
6. api:docs:check
7. test:unit
8. test:integration
9. test:ci
10. build:verify
11. build:size-check
12. security:scan
13. deps:check
14. audit:prod:ci
15. release -- --check-current
```

但应遵守以下覆盖规则：

1. 若 `test:ci` 已完整调用 `test:unit` 与 `test:integration`：

   * 优先分别执行 leaf scripts 以获得精细证据；
   * `test:ci` 仍运行一次，用于验证 CI 总入口；
   * 不重复执行其内部同一套测试超过一次；
   * 无法避免的重复在台账标记。
2. 若 `test` 仅为 `test:unit` 的别名，不重复执行。
3. `release -- --check-current` 只有在确认：

   * 不创建 tag；
   * 不修改版本；
   * 不推送；
   * 不发布；
   * 不写远程服务；

   才能执行，否则记为 `NOT_RUN_REMOTE_WRITE_RISK`。
4. 任何 API drift 或 docs 命令若会生成或覆盖文件，只允许：

   * 使用纯 check 模式；
   * 或先确认输出只进入临时目录；
   * 不允许执行自动修正模式。

## 2.3 每条命令必须记录

* 精确命令；
* 当前目录；
* 环境变量名称，不记录敏感值；
* 开始时间；
* 结束时间；
* 总时长；
* 退出码；
* stdout；
* stderr；
* 生成文件；
* Git 状态变化；
* 是否重跑；
* 与其他脚本的包含关系。

## 原因

质量脚本必须作为独立证据，而不是只在最终报告中写“已通过”。

## 输入

* 脚本 DAG；
* 冻结依赖；
* 当前提交。

## 输出

* 每条命令独立日志；
* `command-results.csv`；
* `test-summary.md`；
* `build-summary.md`；
* `security-scan-summary.md`；
* `git-after-local-gates.txt`。

## 验收标准

* 每个强制本地门均有明确结果；
* 退出码、时长和日志完整；
* 没有跟踪文件被修改；
* 未将扫描器无发现解释成“系统绝对安全”；
* 未将自动化测试通过解释成“产品通过”。

## 停止条件

* 跟踪文件发生非预期变化；
* 安装或命令尝试远程写入；
* 发现凭据泄漏或源码上传行为；
* 机器资源持续耗尽；
* 构建或测试工具进入不可终止的循环。

## 证据层

# 阶段 3：风险驱动的源码与测试有效性审计

## 目标

识别自动化门未覆盖的逻辑缺陷、状态缺陷、权限风险和测试盲区。

## 具体动作

## 3.1 全量审计对象

以下对象必须 100% 盘点和审阅：

* 路由注册及路由守卫；
* 登录、登出、账号切换和会话恢复；
* API client、请求拦截器、响应拦截器；
* 令牌、身份和租户信息存储；
* Zustand store 及持久化；
* 全局错误边界；
* 上传、下载、导出；
* 创建、编辑、提交、删除；
* 管理员或高权限入口；
* 外部链接、重定向；
* 富文本、HTML 注入或用户内容渲染；
* 环境变量和功能开关；
* 日志、监控和错误上报；
* service worker、缓存或离线逻辑，如存在。

## 3.2 重点问题

### 正确性

* 空值、边界值和异常数据；
* 路由参数缺失；
* 页面刷新和深链接；
* 浏览器前进、后退；
* 重复点击；
* 表单重复提交；
* 数据未保存提示；
* 分页、筛选和排序状态；
* 长文本、超大列表和空列表；
* 日期、时区和区域格式。

### 异步状态

* loading、success、empty、error 是否互斥；
* 旧请求覆盖新请求；
* 组件卸载后的状态更新；
* 请求取消；
* 并发提交；
* 429、超时和重试；
* 乐观更新失败后的回滚；
* 上传中断和重新选择；
* SSE、WebSocket 或流式响应，如存在。

### 授权与数据隔离

* 前端路由守卫是否只作为体验控制；
* 401 与 403 是否正确区分；
* 登出后内存、localStorage、sessionStorage、IndexedDB 是否清理；
* 账号切换后是否残留上一账号数据；
* URL、缓存和日志是否泄漏敏感数据；
* 不同租户或角色数据是否可能混用。

### React 19 与状态管理

仅根据实际代码确认，不预设存在问题：

* effect 依赖和闭包陈旧；
* render 中副作用；
* Strict Mode 下重复执行；
* 异步 action 的竞态；
* selector 过宽导致无意义重渲染；
* store 持久化迁移；
* suspense、lazy 和 error boundary 配合；
* 不稳定 key 和列表状态错位。

### 测试有效性

* 测试是否只验证 mock 返回值；
* 是否有无断言测试；
* 是否过度依赖快照；
* 是否跳过高风险分支；
* 是否只测试成功路径；
* 是否忽略请求顺序、取消和错误恢复；
* Playwright 是否实际验证用户可见结果，而非仅等待元素出现。

## 原因

类型、Lint 和测试的退出码不能证明测试断言有效，也不能发现全部业务逻辑与授权边界问题。

## 输入

* 风险登记表；
* 路由、API、store、测试清单；
* 阶段 2 失败和告警。

## 输出

* `source-review-log.csv`；
* `test-effectiveness-map.csv`；
* `unreviewed-files.csv`；
* 初步发现记录；
* 根因候选图。

## 验收标准

* 所有高风险对象均有审阅记录；
* 每个核心旅程至少映射到源码、测试和浏览器验证三者中的两者；
* 未审阅文件数量和原因透明；
* 所有发现包含文件与行号，或明确说明无法定位到单一行。

## 停止条件

* 发现疑似有效凭据、私钥或生产令牌：停止相关文件传播并按 P0/P1 处理；
* 发现继续复现会产生真实数据写入或破坏；
* 依赖外部后端或账号才能继续确认，转入 E3/E4 待确认队列。

## 证据层

E1。

# 阶段 4：生产构建 preview 与 Playwright 主审计

## 目标

验证当前提交的生产构建在受控浏览器中的真实用户行为，而不是仅验证 dev server。

## 具体动作

1. 使用项目正式生产构建命令生成产物。
2. 使用 Vite preview 或项目定义的等价生产预览服务。
3. 记录：

   * 构建产物目录；
   * preview 端口；
   * base path；
   * 环境变量模式；
   * source map 状态；
   * 实际页面资源 URL。
4. 确认 Playwright：

   * `baseURL` 指向 preview；
   * 未隐式重新启动 dev server；
   * 未使用与生产构建不同的 mock 路由，除非该 mock 是本轮明确设计的错误状态注入。
5. 浏览器主证据优先级：

   * 首选 Playwright Chromium；
   * Firefox/WebKit 是否必测取决于项目支持矩阵，需现场确认；
   * 真实 Chrome 仅作为 E3 补充，不替代 E2 可复现脚本。
6. 每条核心旅程至少采集：

   * 初始截图；
   * 关键动作截图；
   * 最终结果截图；
   * console 日志；
   * failed request 和异常响应；
   * Playwright trace；
   * 必要时视频。
7. 对关键交互执行：

   * 键盘完整操作；
   * 焦点顺序；
   * Escape 关闭；
   * Tab/Shift+Tab；
   * Enter/Space；
   * 页面刷新；
   * 前进/后退；
   * 深链接；
   * 连续快速点击；
   * 请求超时、401、403、404、409、422、429、500；
   * 离线或连接失败；
   * 长文本和空数据；
   * 320 CSS px 重排；
   * 200% 缩放。

## 原因

生产构建可能与开发模式在路由、资源路径、环境变量、懒加载、压缩和异常处理上不同。

## 输入

* 成功的生产构建；
* 路由清单；
* 核心旅程和状态组合；
* 专用测试数据或 mocks。

## 输出

* `preview-config.md`；
* `journey-results.csv`；
* Playwright 报告；
* trace、截图、console、network 证据；
* `accessibility-preview.md`；
* `responsive-preview.md`；
* `browser-defects.md`。

## 验收标准

* preview 确认服务于当前 `e605afc` 的生产构建；
* 核心用户旅程均有结果；
* 无未解释的 console error；
* 无未解释的 failed request；
* 关键交互可键盘完成；
* 错误状态不会出现空白页、无限 loading 或无反馈失败；
* 所有失败均保留首次证据，不因重跑通过而删除。

## 停止条件

* 生产构建失败；
* preview 无法启动或资源基础路径错误；
* Playwright 连接的是 dev server；
* 核心入口无法加载；
* 继续操作会写入真实生产数据；
* 浏览器环境无法稳定复现且已完成一次受控重试。

## 证据层

E2。

# 阶段 5：真实账号、生产证据与专项标准审计

## 目标

仅在必要且有权限时补充真实账号、生产平台、Core Web Vitals 和运行保障证据。

## 具体动作

## 5.1 真实账号 Chrome

仅用于以下场景：

* SSO；
* 第三方 Cookie；
* 真实后端授权；
* 浏览器下载行为；
* 文件选择器；
* 浏览器扩展、企业策略或操作系统能力；
* Playwright 与真实 Chrome 行为差异。

要求：

* 使用专用最小权限测试账号；
* 优先测试租户或隔离环境；
* 使用唯一前缀测试数据，例如 `AUDIT-20260713-<ID>`；
* 不执行不可逆删除、支付、发布或生产提交；
* 无隔离环境时，写操作停在最终确认前；
* 不在日志和截图中保留访问令牌、Cookie、个人信息或真实业务内容；
* 测试结束后按既有安全流程清理测试数据，不擅自删除不明数据。

## 5.2 Core Web Vitals

### E2 可验证

* 实验室 LCP；
* 交互延迟代理指标；
* CLS；
* 长任务；
* 主线程阻塞；
* JS 和 CSS 体积；
* 路由级资源瀑布。

### E4 才能正式验证

* p75 LCP ≤2.5s；
* p75 INP ≤200ms；
* p75 CLS ≤0.1；
* 真实设备、网络、地区和页面分组。

无 E4 时，报告必须写：

> “生产环境 Core Web Vitals p75 未获得外部证据；本轮仅完成 preview 实验室验证，不得据此声明生产 p75 达标。”

## 5.3 WCAG 2.2 AA

自动化检查必须由人工复核。抽样至少包括：

* 页面标题；
* landmark；
* heading 层级；
* 表单 label；
* accessible name；
* 错误识别和建议；
* 状态消息；
* 键盘可操作；
* 焦点可见；
* modal 焦点约束与恢复；
* 对比度；
* 200% 缩放；
* 320 CSS px reflow；
* 非文本内容替代；
* 动画和减少动态效果；
* 拖拽操作是否有非拖拽替代，如存在；
* 目标尺寸和焦点遮挡等 WCAG 2.2 新增相关要求，如适用。

最终表述应为：

* “抽样页面未发现已确认的 WCAG 2.2 AA 违规”，或
* “发现以下 WCAG 2.2 AA 违规”。

不得仅凭自动扫描写“项目完全符合 WCAG”。

## 5.4 OWASP ASVS 5.0

建立控制适用性表：

```text
控制编号
控制主题
是否适用于前端
本地可验证证据
需要后端证据
需要生产证据
状态
理由
```

状态限定为：

* `PASS`
* `FAIL`
* `N/A`
* `NEEDS_EXTERNAL_EVIDENCE`

重点审计前端可见部分：

* 输入与输出编码；
* DOM XSS 风险；
* 富文本和 HTML 渲染；
* URL 与开放重定向；
* 身份信息和令牌存储；
* 敏感数据缓存；
* 错误信息泄漏；
* 安全日志泄漏；
* 前端路由授权假设；
* 文件上传前端校验的边界；
* 第三方资源；
* CSP、SRI、安全响应头的前端依赖假设。

服务器会话、数据库、密码策略、访问控制最终执行、密钥管理等不能由前端仓库单独判定。

## 5.5 监控、发布和回滚

本地可审计：

* 错误监控 SDK 是否接入；
* release/version 是否注入；
* source map 是否配置；
* 敏感数据过滤；
* Error Boundary；
* 未处理 Promise；
* 构建标识；
* 发布脚本是否存在只读检查。

E4 才能确认：

* 事件是否实际到达；
* source map 是否正确解析；
* 告警是否生效；
* 版本与部署是否对应；
* 回滚是否可执行；
* 历史回滚时间与结果。

## 原因

真实账号和生产证据能提高可信度，但也具有数据污染、隐私和远程写入风险，必须独立治理。

## 输入

* E2 发现；
* 专用账号；
* 外部控制台权限；
* 项目生产支持矩阵。

## 输出

* `real-account-evidence.md`；
* `cwv-lab.md`；
* `cwv-field.md`；
* `wcag-sample-report.md`；
* `asvs-applicability.csv`；
* `observability-release-evidence.md`。

## 验收标准

* E3/E4 证据与 E1/E2 明确分开；
* 无凭据和个人数据泄漏；
* 未对生产环境进行未经授权的写入；
* p75 结论只引用 E4；
* ASVS 结论明确限定前端适用范围。

## 停止条件

* 缺少账号、MFA、授权或控制台权限；
* 需要生产写操作；
* 页面包含无法安全脱敏的真实敏感数据；
* 外部控制台操作可能改变告警、部署或发布状态。

## 证据层

E3、E4；缺失时明确标记“需现场确认”。

# 阶段 6：发现定级、去重与根因归并

## 目标

将源码、命令、浏览器和外部证据归并为不重复、可复现、可修复的发现。

## 具体动作

1. 每个发现必须包含：

   * 唯一 ID；
   * 标题；
   * 严重度；
   * 审计域；
   * 状态；
   * 置信度；
   * 证据层；
   * 受影响路由、角色和状态；
   * 文件与行号；
   * 环境；
   * 前置条件；
   * 复现步骤；
   * 预期结果；
   * 实际结果；
   * 用户和业务影响；
   * 技术根因；
   * 证据索引；
   * 最小修复建议；
   * 回归验收标准。
2. 同一根因在多个路由出现：

   * 建立一个主发现；
   * 列出所有影响实例；
   * 不按页面重复创建发现。
3. 不同根因产生相同症状：

   * 分开记录。
4. 不同证据层发现同一问题：

   * 合并为一个发现；
   * E1、E2、E3 证据作为该发现的证据链。
5. 修复责任方、修复方式或风险完全不同：

   * 即使表现相近，也应拆分。
6. 自动化失败后重跑通过：

   * 标记 `FLAKY` 或环境敏感；
   * 首次失败证据保留；
   * 不改写为无问题。
7. 扫描器结果必须人工确认：

   * 误报不进入正式问题清单；
   * 但保留在扫描处置台账。

## 原因

大量重复发现会夸大缺陷数量，也会掩盖真正的系统根因。

## 输入

* 所有证据层发现；
* 命令和浏览器日志；
* 根因候选图。

## 输出

* `findings-master.csv`；
* `findings.md`；
* `dedup-map.csv`；
* `false-positive-log.csv`；
* `root-cause-groups.md`。

## 验收标准

* 每个正式发现都可独立复现或由充分静态证据证明；
* 没有仅凭推测定为 P0/P1 的发现；
* 重复实例已归并；
* 每个发现均有修复后验收标准；
* 建议限制在问题所需范围内。

## 停止条件

* 证据不足以支持严重度；
* 无法区分是产品问题、测试环境问题还是工具问题；
* 根因仍需账号或后端证据，转入待确认项，不强行定性。

## 证据层

E1-E4。

# 阶段 7：最终状态判定与交付

## 目标

形成唯一、可审计、与证据层匹配的最终质量状态。

## 最终状态优先级

按以下顺序判定，前项优先于后项。

### 1. `FAIL`

满足任一条件：

* 存在已确认 P0 或 P1；
* 生产构建失败；
* 核心用户旅程在 preview 或真实账号环境不可用；
* 强制质量门失败且确认不是单纯环境故障；
* 存在授权绕过、敏感数据泄漏、数据损坏或不可恢复丢失；
* 存在明确不满足发布门槛的生产依赖高危问题；
* 审计发现当前提交不适合进入发布候选。

### 2. `BLOCKED_WAITING_FOR_USER`

同时满足：

* 尚无足以直接判定 `FAIL` 的已确认问题；
* 某项强制审计必须依赖用户提供账号、MFA、环境变量、外部控制台或访问许可；
* 缺失证据会直接影响最终通过判定。

例如：必须验证真实账号授权链，但没有可用账号。

### 3. `STATIC_ONLY`

同时满足：

* 已完成 E0 和 E1；
* 未成功完成生产构建 preview 的浏览器验证；
* 阻断原因不是已经确认的产品失败；
* 也不一定需要用户操作，例如本机浏览器环境无法使用。

不得在 `STATIC_ONLY` 下声称产品用户路径通过。

### 4. `PASS_WITH_CONCERNS`

满足：

* 无 P0/P1；
* 强制本地门和核心 preview 旅程通过；
* 存在 P2/P3、偶发问题、较小证据缺口，或缺失生产 p75、监控控制台等补充证据；
* 风险不阻止继续进入下一质量阶段，但必须显式接受。

缺少 E4 的 Core Web Vitals p75 时，原则上最高为 `PASS_WITH_CONCERNS`，除非该生产证据明确被排除在本轮发布门槛外且有书面依据。

### 5. `PASS`

必须全部满足：

* 无开放 P0、P1；
* 无影响发布决策的开放 P2；
* 所有强制本地门通过；
* 核心 preview 用户旅程通过；
* 必须的真实账号场景通过；
* 项目质量标准所需的生产或外部证据已具备；
* 未发现未经解释的 console error、关键 network failure 或数据隔离问题；
* 所有未执行项均为正式批准的 N/A，而非证据缺失。

## 输出

* 最终审计报告；
* 执行摘要；
* 覆盖矩阵；
* 盲区声明；
* 证据索引；
* 修复批次建议；
* 唯一最终质量状态。

## 验收标准

* 最终状态仅为五个允许值之一；
* 计划版本与质量状态分开；
* 每项结论可追溯到证据；
* 未将未知项写成通过；
* 未将本地结果写成生产结果。

# 7. 命令执行、失败分流与资源控制

## 7.1 时间预算

| 命令类别                         |  初始时间预算 |
| ---------------------------- | ------: |
| Git、版本和元数据                   |  2 分钟/项 |
| scripts:test、type-check、lint | 15 分钟/项 |
| API 校验                       | 15 分钟/项 |
| 单元测试                         |   25 分钟 |
| 集成测试                         |   40 分钟 |
| CI 总测试                       |   45 分钟 |
| 构建和体积检查                      | 25 分钟/项 |
| 安全与依赖扫描                      | 30 分钟/项 |
| preview 启动                   |   10 分钟 |
| Playwright 核心套件              |   60 分钟 |
| 单条真实账号旅程                     |   20 分钟 |

这些是审计控制预算，不是对项目性能的要求。

## 7.2 超时处理

1. 到达预算时先检查是否仍有持续输出。
2. 有稳定进展时只允许延长一次，最长增加原预算的 50%。
3. 无输出、CPU/内存异常或疑似死锁时终止。
4. 终止后记录：

   * `TIMEOUT_TOOL_OR_ENVIRONMENT`；
   * `TIMEOUT_PRODUCT_OR_TEST`；
   * `RESOURCE_EXHAUSTION`；
   * `UNKNOWN_TIMEOUT`。
5. 不把环境超时直接定为产品 P1。
6. 若稳定地在相同测试点超时，且源码或浏览器证据表明产品进入无限等待，则按产品缺陷定级。

## 7.3 重跑规则

* 同一命令最多重跑一次。
* 第一次失败必须保留。
* 允许重跑的原因：

  * 临时端口冲突；
  * 已确认的网络抖动；
  * 机器资源不足后受控降低并发；
  * 测试框架偶发启动失败。
* 重跑通过时：

  * 结果标记 `PASS_AFTER_RETRY`；
  * 同时建立 flaky 或环境敏感记录；
  * 不改写为首次通过。
* 不允许通过不断重跑获得绿色结果。

## 7.4 并发控制

1. 首次使用项目默认并发，保持与 CI 配置一致。
2. 出现 OOM 或资源耗尽时：

   * 仅在工具明确支持时，将 worker 降至默认的约 50%；
   * 最多重跑一次；
   * 记录原始失败。
3. 不为加速而擅自提高并发。
4. Playwright 多浏览器不得与高资源构建并行。
5. 安全扫描不得与依赖安装并行。

## 7.5 失败分流

| 失败现象            | 初步分类     | 后续动作                      |
| --------------- | -------- | ------------------------- |
| 命令不存在           | 配置或计划问题  | 核对脚本名称；记录，不自行新增脚本         |
| 退出码非 0 且日志为源码错误 | 产品或代码缺陷  | 建立发现，继续不依赖该产物的检查          |
| 缺少环境变量          | 环境阻断     | 判断是否可用测试值；否则待用户           |
| 需要远程凭据          | 外部证据阻断   | 不猜测、不使用个人凭据               |
| 构建失败            | 发布阻断     | 判定 `FAIL` 候选；preview 无法继续 |
| preview 启动失败    | 构建/配置/环境 | 区分产物问题和端口环境               |
| 浏览器测试失败但手工正常    | 自动化或时序问题 | 读取 trace，最多一次定向重跑         |
| 手工和自动化均失败       | 产品缺陷     | 定级并记录复现                   |
| 测试重跑才通过         | flaky    | 不视为稳定通过                   |
| 扫描器无法联网         | 工具限制     | 记录扫描未完成，不视为无漏洞            |
| 脚本修改跟踪文件        | 审计边界违反   | 立即停止该脚本链并保存差异             |

# 8. 浏览器证据规范与账号/数据隔离

## 8.1 证据命名

```text
BR-E2-J07-auth-normal-desktop-step03-20260713T101530.png
BR-E2-J07-auth-500-desktop-trace-20260713T101602.zip
BR-E3-J03-session-expired-console-20260713T112211.txt
```

命名必须包含：

* 证据层；
* 旅程编号；
* 身份状态；
* 数据或网络状态；
* 视口；
* 步骤；
* 时间戳。

## 8.2 每个浏览器缺陷的最低证据

1. 目标 URL，敏感参数脱敏；
2. 浏览器及版本；
3. 当前提交；
4. 身份和数据状态；
5. 视口和缩放；
6. 精确复现步骤；
7. 预期与实际结果；
8. 截图或视频；
9. console；
10. failed network request；
11. trace；
12. 对应文件和行号，能够定位时必须提供。

## 8.3 日志脱敏

必须清除：

* Authorization；
* Cookie；
* access token；
* refresh token；
* session ID；
* 用户真实姓名、手机号、邮箱；
* 专利或业务文档正文；
* 下载链接中的签名参数；
* 内部租户标识；
* API 密钥。

HAR 只有在确认可脱敏后保存。无法安全脱敏时，只保存请求方法、路径模板、状态码和时长摘要。

## 8.4 账号隔离

优先级：

1. 本地 mock 或 fixture；
2. 专用测试环境；
3. 专用测试租户；
4. 专用最小权限真实账号；
5. 个人或生产账号仅在无替代方案且有明确授权时使用。

真实账号原则：

* 不复用个人日常账号；
* 不使用管理员账号测试普通路径；
* 密码和 MFA 不进入证据；
* 浏览器 profile 独立；
* 测试结束后退出并清理本地会话；
* 不从一个账号切换到另一个账号而不清理站点存储。

## 8.5 数据隔离

* 测试数据统一前缀；
* 测试数据不得与真实业务记录重名；
* 写操作优先使用可回收数据；
* 生产环境无隔离数据时，不执行最终提交；
* 删除测试只针对本轮明确创建且可确认归属的数据；
* 不清理未知缓存、文件或记录；
* 测试产生的数据清单单独交付。

# 9. P0-P3 定级准则

严重度综合考虑：

* 用户影响；
* 影响范围；
* 可利用性或发生概率；
* 数据敏感性；
* 是否有可行绕过；
* 是否可恢复；
* 是否阻断发布；
* 是否违反法定或合同要求。

## P0：灾难性

典型情形：

* 可直接导致大规模敏感数据泄漏；
* 无需特殊条件即可绕过关键授权；
* 生产环境不可逆数据损坏；
* 远程代码执行或等价高危；
* 核心系统完全不可用且无恢复手段；
* 审计过程中发现正在发生的严重安全事件。

要求：

* 必须有直接、可复现或高度确定的证据；
* 立即停止可能扩大影响的复现；
* 最终状态必为 `FAIL`。

## P1：严重

典型情形：

* 核心用户旅程无法完成；
* 登录、提交、保存、上传、导出等核心能力稳定失败；
* 有限条件下的权限绕过或跨账号数据暴露；
* 可导致用户数据丢失、串写或错误覆盖；
* 生产构建失败；
* 高影响 WCAG 阻断导致核心功能对键盘用户不可用；
* 高危生产依赖漏洞且项目既定门槛不允许发布；
* 无合理绕过方式。

最终状态通常为 `FAIL`。

## P2：重要

典型情形：

* 非核心路径显著失败；
* 核心路径存在可靠绕过方式；
* 错误反馈、恢复、响应式或可访问性存在明显缺陷；
* 偶发竞态或 flaky 对稳定性构成现实风险；
* 性能明显偏离预算，但未完全阻断；
* 测试缺口使高风险行为缺乏保障；
* 维护性问题已经直接增加缺陷或发布风险。

可进入 `PASS_WITH_CONCERNS`，但应安排修复。

## P3：一般

典型情形：

* 低影响视觉或文案问题；
* 非关键 console warning；
* 轻微语义、焦点或响应式问题；
* 局部代码重复或复杂度问题，尚未造成现实故障；
* 文档、测试命名或低风险可维护性缺陷。

不应将纯个人偏好、无影响的风格差异或无证据的重构建议列为 P3。

# 10. 去重与根因归并规则

1. **同根因、多页面：**一个发现，列出影响页面。
2. **同页面、多症状、同根因：**一个发现。
3. **同症状、不同根因：**分别建立发现。
4. **同问题、多证据层：**合并发现，丰富证据链。
5. **不同修复责任方：**可以拆分，例如前端错误处理和后端状态码错误。
6. **扫描器重复项：**按依赖根包和实际可达路径归并。
7. **测试失败与产品失败：**

   * 测试正确揭示产品问题：一个产品发现；
   * 测试本身错误：单独测试基础设施发现。
8. **多条依赖漏洞：**

   * 同一依赖、同一升级或缓解措施归并；
   * 不同攻击面或不同修复路径拆分。
9. **无障碍问题：**

   * 同一共享组件导致的多页面问题归并；
   * 页面独有问题单独记录。
10. 主发现严重度按最严重且现实可达的影响确定，不按实例数量简单升级。

# 12. 修复阶段如何与审计阶段解耦

1. 本轮审计基线固定为 `e605afc`。
2. 审计阶段不得：

   * 修改源码；
   * 自动修复 Lint；
   * 更新快照；
   * 修改测试以获得通过；
   * 升级依赖；
   * 提交或部署。
3. 修复建议只描述：

   * 缺陷目标；
   * 最小修复边界；
   * 不得破坏的行为；
   * 回归验收标准。
4. 修复阶段另行建立：

   * 新提交基线；
   * 单独分支或明确修复提交；
   * 发现—修复提交映射；
   * 修复前后证据对比。
5. 每个修复项应先增加或完善可复现测试，但不要求为了测试而重做架构。
6. 依赖升级仅在以下情况下建议：

   * 直接修复已确认漏洞或兼容性问题；
   * 项目现有版本无法通过既定质量门；
   * 有明确影响分析和回滚方案。
7. 不建议：

   * 无关目录重构；
   * 全面替换状态管理；
   * 重做设计系统；
   * 统一格式化全仓库；
   * 为追求“现代化”而升级所有依赖。
8. 修复完成后的复审分两层：

   * 定向复测对应发现；
   * 重新执行全部强制质量门和受影响核心旅程。
9. 旧提交的浏览器通过证据不能直接继承为新提交通过证据。

# 13. “整个项目全面审计”仍无法保证的盲区

即使完整执行本计划，也不能绝对保证以下事项：

1. **服务端授权和数据隔离。**
   前端只能验证表现和接口响应，无法证明后端每个对象级权限控制正确。

2. **生产 Core Web Vitals p75。**
   没有生产 RUM、CrUX 或等价外部数据时不能验证。

3. **生产网络基础设施。**
   CDN、WAF、TLS、缓存策略、压缩、HTTP 安全头和网关限流需要生产证据。

4. **所有真实角色和租户。**
   未提供的角色、地区、租户和功能开关不能覆盖。

5. **所有浏览器和设备。**
   未确认正式支持矩阵时，不能声称覆盖全部浏览器、手机和操作系统。

6. **真实辅助技术兼容性。**
   自动扫描和键盘检查不能完全替代 NVDA、JAWS、VoiceOver 等人工验证。

7. **长期稳定性。**
   数小时或数天运行后的内存泄漏、连接积累和缓存膨胀需要长时测试。

8. **高并发和容量。**
   前端本地审计不能证明后端、CDN 和浏览器在真实高并发下稳定。

9. **第三方服务故障。**
   登录、支付、文件存储、监控、验证码等第三方的真实故障模式可能无法模拟。

10. **生产发布和回滚真实可用性。**
    只看脚本和配置不能证明发布平台、权限和回滚操作可用。

11. **零日漏洞和未知供应链风险。**
    依赖扫描只能覆盖已知数据库和扫描器规则。

12. **产品需求正确性。**
    没有正式需求、验收标准和产品负责人确认时，只能验证实现一致性和通用质量，不能证明产品行为符合全部业务意图。

13. **非代码资产。**
    法律文本、隐私政策、版权、商标、数据合规和内容准确性不属于纯前端技术审计可完整证明的范围。

14. **未触达的隐藏路由和功能开关。**
    动态配置、灰度开关和仅生产开启功能需要外部配置证据。

15. **测试数据代表性。**
    受控 fixture 无法覆盖所有真实用户输入、文档尺寸和历史脏数据。

最终报告必须列出：

* 实际覆盖率；
* 未覆盖路由；
* 未覆盖角色；
* 未覆盖环境；
* 未执行命令；
* 未获得的 E3/E4 证据；
* 对最终状态的影响。

# 14. 最终推荐的精简执行清单

1. 核对分支、HEAD、工作树和仓库路径。
2. 在仓库外建立证据目录，记录环境和文件哈希。
3. 禁止修复、快照更新、依赖升级、远程写入和源码上传。
4. 读取 `package.json`、锁文件和所有质量脚本。
5. 展开脚本调用图和副作用，确认 `release -- --check-current` 是否只读。
6. 盘点全部路由、API、store、权限边界、上传下载和错误处理。
7. 建立核心旅程、风险评分和覆盖契约。
8. 使用冻结模式恢复依赖，确认锁文件不变。
9. 按顺序执行脚本测试、类型、Lint、API、单元、集成、CI、构建、包体、安全和依赖检查。
10. 对每条命令保存退出码、时长、完整日志和前后 Git 状态。
11. 对高风险源码和对应测试进行深入审阅。
12. 生成生产构建并启动 preview。
13. 确认 Playwright 指向 preview，而不是 dev server。
14. 执行核心旅程、错误状态、键盘、320 CSS px、200% 缩放和重复操作测试。
15. 保存截图、trace、console、network，并进行敏感信息脱敏。
16. 仅在必要时使用专用真实账号 Chrome 补充验证。
17. 将 WCAG 自动结果人工复核，将 ASVS 限定为前端适用控制。
18. 将本地性能与生产 p75 严格分开。
19. 按 P0-P3 定级，同根因问题归并。
20. 输出证据索引、覆盖矩阵、盲区、修复批次和唯一最终质量状态。
21. 最后再次核对 Git 状态，确认没有跟踪文件、提交或远程环境被修改。

# 15. 最终审计结论

原计划的方向正确，审计域覆盖较广，但缺乏以下决定性能力：

* 可复现执行能力；
* 脚本副作用控制；
* 浏览器抽样决策；
* 多层证据隔离；
* 超时和偶发失败处理；
* P0-P3 统一定级；
* 五种最终状态的排他判定；
* 对生产 p75、ASVS 和发布回滚证据边界的限定。

采用本增强版后，审计将形成以下闭环：

```text
固定提交
→ 冻结只读边界
→ 展开脚本与架构
→ 运行本地质量门
→ 风险驱动源码审阅
→ 生产构建 preview
→ Playwright 用户旅程
→ 必要的真实账号和生产证据
→ 根因归并
→ 唯一质量状态
→ 独立修复批次
```

该闭环可以显著降低“测试通过即产品通过”“本地通过即生产通过”“扫描无告警即安全通过”和“抽样检查即全面覆盖”等错误结论。
