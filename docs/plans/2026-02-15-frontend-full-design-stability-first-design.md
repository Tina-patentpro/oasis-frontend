# 前端全量设计方案（稳定性优先）设计文档

> 日期：2026-02-15  
> 状态：已评审通过（用户确认：全部通过）  
> 适用范围：全站前端（工作台、项目会话、认证、计费、通知、设置）

## 1. 设计目标

本方案采用“先稳定、后提效”的双层策略，以稳定性为第一优先级，同时提升业务效率。

### 1.1 核心目标

- 稳定性目标：
  - `crash-free session >= 99.95%`
  - 可重试类请求自动恢复成功率 `>= 85%`
  - 关键流程异常后支持原位恢复，不依赖整页刷新
- 效率目标：
  - 核心任务链路（选工具 -> 输入 -> 生成 -> 导出）`P95 完成时长下降 25%`
  - 高频操作点击步数下降 `20%`

### 1.2 成功判定

- 线上监控指标达到目标阈值并持续稳定
- 回归测试通过，关键链路无阻断性问题
- 用户侧反馈“可恢复、可预期、可快速完成任务”

## 2. 总体架构设计

### 2.1 架构分层

- `App Shell + Domain Modules`：按业务域拆分，降低耦合
- `Reliability Layer`：统一超时、重试、取消、去重、错误映射、降级策略
- `State Layer`：服务端状态与本地 UI 状态分离，写操作支持乐观更新与回滚
- `Design Token Layer`：颜色/间距/字号/阴影/动效参数化，统一主题变量
- `Observability Layer`：错误、性能、业务链路三类埋点统一采集

### 2.2 设计原则

- 稳定优先：先保证“不中断、可恢复”
- 保持一致：同类错误、同类任务状态采用一致交互语言
- 渐进改造：不一次性推翻，按模块灰度上线
- 可观测驱动：每次改造必须有指标对照与回归证据

## 3. 全站模块设计

### 3.1 工作台（核心主链路）

- 左栏：工具/项目/会话统一检索，常驻筛选与快捷键入口
- 中栏：输入卡片“必填优先 + 高级折叠”，提交前本地校验
- 右栏：输出区引入稳定态视图（成功/部分成功/失败/重试中）
- 生成链路：步骤状态可回放，失败可原位重试与续跑

### 3.2 项目与会话模块

- 列表交互统一（分页、搜索、筛选、批量）
- 批量操作失败进入“重试队列”
- 高风险操作支持短时撤销

### 3.3 认证与账户模块

- Token 刷新失败与会话过期采用统一恢复路径
- 避免无提示跳转，明确当前状态与下一步动作

### 3.4 计费、通知、设置模块

- 计费关键字段（余额/订单状态）采用强一致展示与异常补偿提示
- 通知中心支持故障类消息聚合、已读策略一致化
- 设置页按“稳定性相关能力”前置排序

## 4. 数据流与容错策略

### 4.1 读取链路

- 采用 `cache-first + stale-while-revalidate`
- 优先展示缓存结果，后台更新并静默刷新

### 4.2 写入链路

- 幂等键 + 去重 + 指数退避重试
- 乐观更新失败后自动回滚，并给出明确反馈

### 4.3 长任务链路（生成/导出）

- 统一任务状态机：`queued/running/partial_success/failed/canceled/success`
- 状态可追踪、可中断、可恢复

### 4.4 流式与文件链路

- SSE 断流重连 + 最近有效状态保留
- 上传下载提供进度可视化与失败原因分级（网络/鉴权/服务端）

## 5. 测试与发布策略

### 5.1 稳定性测试

- 网络抖动、超时、502/504、鉴权失效、并发冲突
- 页面恢复能力与任务连续性验证

### 5.2 效率测试

- 核心链路时长（P50/P95）
- 列表性能（大数据量）
- 操作步数与响应时间

### 5.3 发布治理

- 灰度顺序：工作台 -> 项目会话 -> 设置计费
- 发布门禁：错误率、失败率、链路成功率达标后扩大流量
- 回滚策略：模块级快速回滚与开关控制

## 6. 分阶段实施路线

- `Phase 0（1周）`：指标基线、埋点补齐、风险清单冻结
- `Phase 1（2周）`：统一可靠性底座（请求/错误/降级/状态机）
- `Phase 2（2周）`：工作台主链路改造（稳定性 + 效率）
- `Phase 3（2周）`：项目会话、认证计费、设置通知收口

## 7. 风险与边界

- 风险：
  - 存量逻辑分散，统一策略落地初期可能引发回归
  - 指标体系不足会导致“优化效果不可证”
- 边界：
  - 本文档仅定义前端全量设计，不含后端接口变更方案
  - 与后端协同事项通过接口契约文档单独跟踪
